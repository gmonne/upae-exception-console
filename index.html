UPAE · Reference

How this tool works, and where it's headed

This page explains the two systems UPAE depends on — CMiC and the AI layer — in plain terms, and what happens between this mock-up and a live pilot.

How CMiC APIs will be used

U.S. Payroll / HCM only

UPAE reads from CMiC's US Payroll and HCM APIs — the same system Payroll already uses to run weekly payroll. UPAE doesn't replace CMiC or change how payroll is entered; it pulls the data CMiC already holds, checks it, and sends exceptions back to a reviewer before that payroll run is finalized. These APIs are request/response (UPAE asks CMiC for data on a schedule) rather than a live feed, so the integration runs on a polling cadence tied to the weekly pay cycle rather than instantaneous updates.

What UPAE pullsCMiC sourceWhy UPAE needs it
Timesheets & hours pyctimeempint Employee, job, cost code, and hours for every entry — the core record every check runs against.
Employees, unions & trades pyemployee, pyunions, pytrades Confirms each employee is paid under the correct union and classification.
Pay rates Trade / Union / Job Pay Rates The contracted rate each hour should have been paid at, for overtime and base-rate checks.
Benefits & deductions Benefit & Deduction Codes Confirms fringe and deduction contributions were applied.
Job & cost codes jcjob, jcjobcostcodes The approved cost-code list each job's hours must be allocated to.
Pay period & cutoff Pay Runs, Job Pay Groups Tells UPAE which pay period is open and when it closes.

Full endpoint-level detail is in the UPAE Technical Document, Section 6.3 (CMiC API Mapping).

How AI will be used

Advisory by design

AI does not touch payroll directly. It only flags things for a person to review — the rules engine is what's allowed to auto-resolve, and only for narrow, deterministic cases like an exact duplicate entry.

1
Spot unusual patterns
Compares each timesheet entry to that employee's own history and their crew's typical pattern — hours, cost-code splits, classification changes — and flags what doesn't fit. Every flag comes with a confidence score and a plain-language reason, shown in the Exception queue.
2
Learn from what reviewers decide
Every time a reviewer confirms, dismisses, or corrects a flagged item, that decision is recorded and used to tune future flags — so the model stops repeating flags people keep dismissing.
3
Assist the reviewer (future)
Once there's a track record of flags and resolutions, a later version can prioritize a reviewer's queue by risk, and draft a plain-language summary of what's happening and why — still for a person to act on, not to act on its own.

Technology & estimated cost

Microsoft Azure · GitHub

This showcase runs on GitHub (source & auto-deploy) and the Azure Static Web Apps free tier — enough for a single-page demo, but not the full pilot architecture. A working pilot adds a real integration layer, a rules/AI engine, and a database behind the console:

LayerAzure serviceRole
Front endStatic Web AppsHosts the console UI; auto-deploys from GitHub on every push.
Integration & rulesFunctionsPolls CMiC on a schedule, runs the rules engine and AI scoring. Serverless — scales to zero between runs.
Structured dataSQL DatabasePayroll transactions, exceptions, and resolution history — the auditable system of record.
Raw data & logsBlob StorageRaw CMiC payloads, exports, and integration logs.
SecretsKey VaultCMiC service-account credentials — never stored in code.
Sign-inEntra IDReviewers sign in with existing organizational accounts.
